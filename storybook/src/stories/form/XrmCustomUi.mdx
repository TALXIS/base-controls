<Title>Custom UI</Title>
<Subtitle>Override parts of the Xrm presentation layer while keeping the same underlying form runtime.</Subtitle>

<div className="form-docs-copy">
  <p>The Xrm custom UI surface is about replacing presentation, not replacing the form model.</p>
  <p>
    <code>XrmForm</code> still loads data through the same strategy, still binds controls to the same record fields, and still keeps the same runtime lifecycle. What changes is how selected parts of that form are rendered.
  </p>
  <p>
    That replacement is not limited to a single built-in visual variant. In practice, consumers can provide their own components for the parts of the Xrm form they want to own, while still leaving the underlying runtime, binding, and save lifecycle to <code>XrmForm</code>.
  </p>
</div>

<Heading>Using your own components with form hooks</Heading>

<div className="form-docs-copy">
  <p>
    Custom Xrm UI components can still communicate with the form through the same hooks used by the base Form runtime. The most important example is <code>useField</code>, which lets a custom control read the current field value and push updates back into the live form model.
  </p>
  <p>
    This is what makes custom rendering practical: the component can be completely your own, but the data binding, validation flow, and persistence still run through the shared form infrastructure instead of being reimplemented manually.
  </p>
</div>

<Heading>Custom controls</Heading>

<div className="form-docs-copy">
  <p>
    Use top-level <code>components</code> overrides when specific control ids need custom rendering. This is the pattern to use when only a few fields or controls should look or behave differently, while the rest of the form should continue to use the stock rendering pipeline.
  </p>
  <p>
    This keeps the customization targeted. The custom control takes over only where you explicitly map it, and the remaining controls still fall back to the standard implementation.
  </p>
  <p>
    Those custom controls can still use hooks such as <code>useField</code> to work with the live field state. That keeps the control implementation custom while preserving the same form behavior underneath.
  </p>
  <p>
    Use <a href="./?path=/story/form-xrm-custom-ui--custom-controls">Form / Xrm / Custom UI / Custom Controls</a> for the focused preview. That story now keeps the injected code, data, and FormXml editors directly in the same Custom Controls surface instead of splitting them into separate sidebar stories.
  </p>
</div>

<Heading>Custom tabs</Heading>

<div className="form-docs-copy">
  <p>
    Use <code>components.tabs.onRenderTabs</code> when the form tabs should be presented differently but the underlying tab structure should remain intact.
  </p>
  <p>
    That is the same idea as the React compose tabs override: the form still owns which tabs exist and which one is selected, but the navigation UI can be swapped for something that fits the product experience better.
  </p>
  <p>
    Use <a href="./?path=/story/form-xrm-custom-ui--custom-tabs">Form / Xrm / Custom UI / Custom Tabs</a> for the horizontal tabs override and <a href="./?path=/story/form-xrm-custom-ui--custom-tabs-vertical">Custom Tabs Vertical</a> for the same pattern with a vertical navigation layout.
  </p>
</div>

<Heading>When to use this section</Heading>

<div className="form-docs-copy">
  <p>
    Choose this approach when the standard Xrm rendering is close, but not quite the final experience you need. It lets you keep the same form model, the same data binding, and the same Xrm-aware runtime, while selectively replacing the presentation layer.
  </p>
</div>
